# OpenCode v2 插件迁移方案（opencode-token-board）

> 日期：2026-10-12  
> 状态：**方案待定稿** —— 只做调研与设计，尚未改动任何代码  
> 结论一句话：OpenCode v2 是插件 API **硬断代**，必须做代码级移植，改配置无效。

---

## 一、背景与根因

### 1.1 现象

本机 OpenCode 升级后，插件不再生效。

### 1.2 实测环境

| 项                                | 值                                              |
| -------------------------------- | ---------------------------------------------- |
| OpenCode CLI                     | **2.0.27**（包名已由 `opencode` 变为 `@opencode/cli`） |
| 本插件版本                            | 0.2.0（`package.json`）                          |
| 插件编译所用 SDK                       | `@opencode-ai/plugin` **1.14.48**（v1 时代）       |
| `@opencode-ai/plugin` npm latest | 1.19.0（v1 线最高版本）                               |

### 1.3 根因（官方文档原文）

> V1 plugin implementations do not run in V2. Moving a file or renaming its config entry is not enough.

v2 加载 v1 插件时报错并跳过：

```
Plugin must export a default definition with an id and an effect or setup function.
(cause: SchemaError(Expected object at ["default"]))
```

v2 的三项**有意为之的破坏性变更**：

1. 插件 API —— 全新契约，v1 实现不运行
2. 服务端 API 与客户端契约 —— 通信层替换
3. 终端客户端配置 —— 分层的 `tui.json(c)` 收敛为单个全局 `cli.json`（首次启动自动迁移）

> 附带一条：v2 **接受但不执行** LSP 配置。若插件依赖 LSP 诊断，会静默失效。本插件不依赖 LSP，无影响。

## 三、v1 → v2 契约对照（核心）

### 3.0 总表

| #  | 维度      | v1                                                      | v2                                                                                                                  |
| -- | ------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 1  | 依赖包     | `@opencode-ai/plugin`（含 `/tui`）                         | `@opencode/plugin`（服务端）/ `@opencode/plugin/tui`（CLI/TUI，运行时解析，无需安装）                                                 |
| 2  | 导出形态    | 裸 async 函数，或 `{ id, server }` / `{ id, tui }`           | `export default Plugin.define({ id, setup(ctx) {...} })`                                                            |
| 3  | 生命周期清理  | 返回 `dispose` hook                                       | `setup` **返回一个 cleanup 函数**                                                                                         |
| 4  | 上下文     | `{ directory, project, client, $ }`                     | `ctx.location.directory` / `ctx.location.project`，能力按**域**分组                                                        |
| 5  | 事件订阅    | `api.event.on(type, cb)`，payload 在 `event.properties.*` | 服务端：`for await (const e of ctx.event.subscribe({signal}))`；CLI：`context.data.on(type, cb)`；payload 在 `event.data.*` |
| 6  | 状态存储    | `api.kv.get/set`（同步）                                    | `ctx.storage.get/set`（**异步，需 await**）                                                                               |
| 7  | 注册入口    | `api.command.register()` / `api.slots.register()`       | `context.keymap.layer()` / `context.ui.slot()`                                                                      |
| 8  | 自定义工具   | `tool()` 助手 + **Zod** schema                            | `ctx.tool.transform(editor => editor.add(...))` + **JSON Schema**                                                   |
| 9  | Hook 注册 | 返回 `"tool.execute.before": (input, output) => {}`       | 按域注册：`ctx.tool.hook("execute.before", (event) => {})`，**单个可变 event**                                                |
| 10 | 配置键     | `plugin` + `[pkg, options]` 元组                          | `plugins` + `{ package, options }` 对象                                                                               |
| 11 | 本地发现目录  | `.opencode/plugin/`                                     | `.opencode/plugins/`（复数）                                                                                            |

### 3.1 入口导出

**v1** —— `src/server.ts`

```ts
import type { PluginModule } from "@opencode-ai/plugin"

const plugin: PluginModule & { id: string } = {
  id: "opencode-token-board",
  server: async () => {
    return {}
  },
}

export default plugin
```

**v2**

```ts
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "opencode-token-board",
  async setup(ctx) {
    // 本插件服务端目前无逻辑，占位即可
  },
})
```

**v1** —— `src/tui.tsx`

```ts
import type { TuiPluginModule } from "@opencode-ai/plugin/tui"

const tui: TuiPluginModule["tui"] = async (api) => {
  /* ... */
}

const plugin: TuiPluginModule & { id: string } = {
  id: "opencode-token-board",
  tui,
}

export default plugin
```

**v2**

```ts
import { Plugin } from "@opencode/plugin/tui"

export default Plugin.define({
  id: "opencode-token-board",
  async setup(context) {
    const cleanups: (() => void)[] = []
    /* ... 注册逻辑 ... */

    // 替代 v1 的 api.lifecycle.onDispose
    return () => {
      for (const cleanup of cleanups) cleanup()
    }
  },
})
```

> 注意：`id` 在 v2 不只是标识 —— **插件存储按 id 分作用域**，且出现在状态与诊断信息里。必须唯一且稳定，不要随版本改名。

### 3.2 事件订阅

**v1** —— `src/tui.tsx:69`

```ts
const unsubMsgUpdated = api.event.on("message.updated", (event: any) => {
  const info = event.properties?.info
  // ...
})
cleanups.push(unsubMsgUpdated)
```

**v2（CLI / TUI 侧，本插件适用）**

```ts
const stopMsgUpdated = context.data.on("message.updated", (event) => {
  const info = event.data.info          // properties → data
  // ...
})
cleanups.push(stopMsgUpdated)
```

**v2（服务端侧，对照用）**

```ts
const controller = new AbortController()
void (async () => {
  for await (const event of ctx.event.subscribe({ signal: controller.signal })) {
    if (event.type === "session.idle") { /* ... */ }
  }
})()
return () => controller.abort()
```

涉及改动点（`src/tui.tsx`）：`message.updated`、`message.part.updated`、`message.removed`、`session.idle`、`permission.asked`、`permission.replied`，共 **6 处**。

### 3.3 状态存储

**v1** —— 同步读写，共 **15 处**（`tui.tsx` / `commands.tsx` / `sidebar.tsx`）

```ts
api.kv?.set?.("tokenwatch-config", cfg)
const cfg = api.kv?.get?.("tokenwatch-config") as SidebarConfig | undefined
```

**v2**（按服务端迁移指南）

```ts
await ctx.storage.set("settings", { strict })
const settings = await ctx.storage.get("settings")
```

⚠ **这里藏着一个结构性影响**：`api.kv` 是**同步**的，而 `ctx.storage` 是**异步**的。`sidebar.tsx` 目前在渲染路径里同步读 kv（配置、折叠状态、会话消息缓存）。改成 await 后不能直接在 render 里读，需要：

> 引入一层**内存缓存 signal** —— `setup` 时一次性 `await storage.get()` 灌入内存，之后渲染读内存；写入时先更新内存再异步落盘。

⚠ **待确认（实现前置）**：`ctx.storage` 是**服务端** context 的成员，文档明确。但 CLI/TUI 插件页列出的 context 成员为 `options / location / app / client / renderer / theme / data / ui / keymap`，只提到 "cached data"，**未点名 storage 成员名**。需在实现第一步先确认 CLI context 的持久化 API，否则后面 15 处改动会返工。

### 3.4 命令注册

**v1** —— `src/commands.tsx:21`

```ts
api.command?.register(() => [
  {
    value: "tokenwatch-usage",
    title: "TokenWatch",
    description: "Token usage reports, export, and settings",
    category: "Stats",
    slash: { name: "usage" },
    onSelect: async (dialog) => {
      if (dialog) showUsageMenu(api, dialog)
    },
  },
])
```

**v2**

```ts
context.keymap.layer(() => ({
  mode: "global",
  commands: [
    {
      id: "tokenwatch-usage",
      title: "TokenWatch",
      slash: { name: "usage" },
      run: () => {
        context.ui.panel.open("tokenwatch.usage")
      },
    },
  ],
}))
```

⚠ v1 的 `onSelect(dialog)` 回调在 v2 **没有对应物** —— 现有那套「命令 → 弹出多级菜单」的交互链需要重新设计（见 3.5 / 3.6）。

### 3.5 槽位注册（**最大风险点**）

**v1** —— `src/tui.tsx:210`

```tsx
api.slots.register({
  order: 50,
  slots: {
    sidebar_content: (_ctx, { session_id }) => (
      <TokenWatchPanel api={api} theme={api.theme} messages={() => api.state.session.messages(session_id)} />
    ),
  },
})
```

**v2（官方 CLI 文档只给出两个槽）**

```tsx
// ① 面板贡献
context.ui.slot({
  append: "session.panel",
  render: (panel) => (
    <Show when={panel.name === "tokenwatch.usage"}>
      <TokenWatchPanel panel={panel} />
    </Show>
  ),
})

// ② app 槽里挂键盘层 / 命令
context.ui.slot({
  append: "app",
  render: () => {
    context.keymap.layer(() => ({ /* commands */ }))
    return null
  },
})
```

⚠ **`sidebar_content` 这个槽位在 v2 文档中未出现**。v2 明确的两个槽是：

| 槽               | 形态               | 打开方式                                                 |
| --------------- | ---------------- | ---------------------------------------------------- |
| `session.panel` | 会话面板，宿主管尺寸/焦点/全屏 | `context.ui.panel.open(name, { presentation })` 显式打开 |
| `app`           | 应用级插槽            | 常驻                                                   |

这意味着「**常驻侧边栏**」这一形态可能无法原样保留。三条备选路线：

| 路线                    | 说明               | 代价              |
| --------------------- | ---------------- | --------------- |
| A. 改用 `session.panel` | 用户通过命令/快捷键主动打开面板 | 失去"常驻可见"，交互形态变化 |
| B. 运行时枚举实际可用槽         | v2 可能仍有未文档化的侧栏槽  | 需实测确认，有不确定性     |
| C. 降级为 `app` 槽内自绘     | 在 app 槽里渲染紧凑状态条  | 布局能力受限，需重做 UI   |

建议**先做路线 B 的实测**（用 `opencode plugin list --builtin` + 运行时探测），拿到真实槽位清单后再在 A/C 之间定夺。

### 3.6 Dialog / Toast

**v1** —— `commands.tsx` / `tui.tsx`

```tsx
api.ui.toast?.({ message: "Report saved", variant: "info" })

dialog.replace(() => (
  <api.ui.DialogSelect title={t("settingsTitle")} options={[...]} flat />
))
```

**v2**

```ts
context.ui.toast.show({ message: "Report saved", variant: "success" })
// DialogSelect / DialogPrompt / TuiDialogStack 在 v2 文档中无对应
```

⚠ **待确认**：v2 是否有等价的 dialog stack 组件。若没有，现有 5 个 `DialogSelect` / `DialogPrompt` 菜单（用量菜单、HTML 报告范围、设置、Go 配置、Go 字段输入）需要改成 panel 承载，或自绘。

| v1                                                | v2                                                    | 备注                             |
| ------------------------------------------------- | ----------------------------------------------------- | ------------------------------ |
| `api.state.session.messages(sessionID)`           | 未见对应；服务端为 `ctx.session.get({ sessionID })`            | CLI 侧待确认，可能改走 `context.client` |
| `api.state.config`                                | 未见对应                                                  | 同上                             |

## 四、本插件改造清单

按文件统计，标注规模与风险：

| #  | 文件                     | v1 用法                                      | v2 目标                                 | 规模    | 风险         |
| -- | ---------------------- | ------------------------------------------ | ------------------------------------- | ----- | ---------- |
| 1  | `src/server.ts`        | `{ id, server }`                           | `Plugin.define({ id, setup })`        | 小     | 低          |
| 2  | `src/tui.tsx`          | `TuiPluginModule["tui"] = async (api)`     | `Plugin.define({ id, setup })`        | 中大    | 低          |
| 3  | `src/tui.tsx`          | `api.event.on` ×6                          | `context.data.on`                     | 中     | 低          |
| 4  | `tui/commands/sidebar` | `api.kv` ×15（同步）                           | `context.storage`（异步，需加内存缓存层）         | 中     | **中**      |
| 5  | `src/commands.tsx`     | `api.command.register`                     | `context.keymap.layer`                | 中     | 中（交互需重设计）  |
| 6  | `src/tui.tsx:210`      | `slots.register("sidebar_content")`        | `context.ui.slot("session.panel")`    | **大** | **高**      |
| 7  | `commands/tui`         | `api.ui.toast` ×8、`DialogSelect/Prompt` ×5 | `context.ui.toast.show` + 新 dialog 方案 | 中     | **中高**     |
| 8  | `sidebar.tsx`          | `api.state.session/ config / part`         | `context.client` / `ctx.session.*`    | 中     | **中**      |
| 9  | `src/notify.ts`        | wscript 拉独立 PowerShell 弹窗                  | v2 内置 attention（通知+音效）                | 小     | 低（**建议砍**） |
| 10 | `package.json`         | `@opentui/core ^0.2.9` + v1 SDK            | `>=0.5.8` + `@opencode/plugin`        | 小     | 低          |

合计约 **60+ 处**调用点。

### 关于 `notify.ts` 的取舍建议

v1 的权限弹窗链路是自建：`permission.asked` → wscript 拉起独立弹窗进程 → 写标记文件 → 轮询读标记 → `permission.reply`。

v2 已内置 attention 机制（`cli.json` 的 `attention.notifications` / `attention.sound`，本机**已开启**），且官方权限事件仍在。这套自建弹窗的**存在理由已基本消失**。

按「能砍则砍」原则，建议：**先评估整体删除**，权限提示退回 v2 原生 attention。若确需在 TUI 内提示，用 `context.ui.toast.show` 即可。这样既减掉 `notify.ts` 的进程/轮询复杂度，也少一个平台兼容面。


## 六、风险与待确认项

| # | 项                                      | 影响                    | 处置              |
| - | -------------------------------------- | --------------------- | --------------- |
| 1 | CLI/TUI context 的**持久化 API 成员名**未在文档点名 | 阻塞 15 处 kv 改动         | 阶段 0 实测确认       |
| 2 | **`sidebar_content` 槽在 v2 是否存在**       | 决定侧边栏形态能否保留           | 阶段 0 实测；备选见 3.5 |
| 3 | v2 是否有 **dialog stack**                | 决定 5 个菜单的改造量          | 阶段 0 实测         |
| 4 | `api.state.*` 在 CLI 侧的新对应物             | 影响 `sidebar.tsx` 数据源  | 阶段 0 / 阶段 5     |
